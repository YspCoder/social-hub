# Snap Conversions API v3 adapter

`snapchat/conversions-api-v3` submits typed Web, Mobile App, and Offline
conversion events to one configured Snap Pixel or Snap App asset. It is a
separate product boundary from `snapchat/marketing-api-v1`: campaign management
and conversion telemetry have different credentials, payloads, privacy rules,
and rate limits.

This adapter follows the current official v3 REST documentation. Snap's
official `business-sdk-go` repository was last updated in January 2023 and
still calls the deprecated `/v2/conversion` endpoints, so it was used only as
a historical field and normalization reference. It is not a dependency of this
package.

The contract and official references below were last verified on 2026-08-25.

## Configuration and authentication

Each social-hub account owns exactly one asset. A `PIXEL` account accepts Web
and Offline events; a `SNAP_APP` account accepts Mobile App events. Keeping
these accounts separate prevents an event from being sent to the wrong asset
class.

The production origin is fixed to `https://tr.snapchat.com/v3`; configuration
cannot replace it. The access token is resolved from `access_token_ref` and
sent in Snap's documented production `access_token` query parameter. The
adapter shallow-clones the configured HTTP client, removes its cookie jar, and
rejects redirects so credentials cannot be stored as cookies or forwarded to
another origin.

```yaml
version: 1
platforms:
  - adapter: snapchat/conversions-api-v3
    product: conversions-api
    accounts:
      - id: store-pixel
        access_token_ref: env://SNAP_CAPI_TOKEN
        settings:
          asset_id: 1ec32188-754e-4be2-8e55-c949a984a39f
          asset_type: PIXEL
      - id: mobile-app
        access_token_ref: env://SNAP_CAPI_TOKEN
        settings:
          asset_id: 0bb12233-4455-6677-8899-aabbccddeeff
          asset_type: SNAP_APP
```

Snap recommends a static long-lived CAPI token generated by an Organization
Admin in Ads Manager. It does not expire or refresh and can address only Pixel
and Snap App assets owned by the same organization. Snap recommends no more
than 1,000 requests per second for that token type. Standard OAuth access
tokens remain subject to the documented 10 requests-per-second limit.

Snap's test-event documentation also contains an OAuth Bearer example, but it
does not define Bearer authentication as the production ingestion contract.
This adapter therefore intentionally implements only the production query-token
form. Callers needing another token placement must wait for an unambiguous Snap
production contract rather than relying on the test-tool example.

## Usage

Importing the package registers the adapter. The typed workflow is available
from `Client.Conversions()`:

```go
import (
    "context"
    "time"

    conversions "social-hub/adapters/snapchat/conversions"
    "social-hub/pkg/socialhub"
)

func sendPurchase(ctx context.Context, common socialhub.Client) error {
    client := common.(*conversions.Client)
    _, err := client.Conversions().SubmitEvents(ctx, []conversions.ServerEvent{{
        EventName:      conversions.EventPurchase,
        EventTime:      time.Now().UnixMilli(),
        EventID:        "order-1001",
        ActionSource:   conversions.ActionSourceWeb,
        EventSourceURL: "https://shop.example/checkout",
        UserData: conversions.UserData{
            Emails:          []string{"buyer@example.com"},
            ClientIPAddress: "192.0.2.10",
            ClientUserAgent: "example-store/1.0",
        },
        CustomData: &conversions.CustomData{
            Value:      "49.95",
            Currency:   "USD",
            ContentIDs: []string{"sku-1"},
            OrderID:    "order-1001",
        },
    }})
    return err
}
```

`Decimal` values are base-10 strings in Go and JSON numbers on the wire. They
never pass through `float64`. Scalar custom properties are split into string,
number, and boolean maps, and the same property name cannot appear in more than
one map.

Only `socialhub.WithCallTimeout` is supported. `WithRequestID` is rejected
because Snap does not define a caller request-ID header, `WithIdempotencyKey`
is rejected because Snap does not define such a header for CAPI, and
`WithFields` is rejected because these endpoints do not support response field
selection. Use a stable per-event `event_id` for deduplication and retry safety.

## Customer data policy

The adapter accepts plaintext or an exact 64-character lowercase SHA-256 value
for hash-required fields. Plaintext is normalized and hashed in a temporary
wire copy; input structs are not mutated. Existing lowercase SHA-256 values are
not hashed again. Uppercase digests and legacy MD5 values are rejected because
their intent is ambiguous.

| Wire fields | Treatment |
|---|---|
| `em`, `ph`, `fn`, `ln`, `ge`, `ct`, `st`, `zp`, `country`, `external_id` | Normalize, SHA-256, deduplicate |
| client IP, user agent, subscription/lead/anonymous/download IDs, `sc_click_id`, `sc_cookie1`, `idfv`, `partner_id` | Validate and send without hashing |
| `madid` | Lowercase and send without hashing, per the current v3 parameter reference |

Every event must provide at least one of: email, phone, the client-IP/user-agent
pair, or a Mobile Advertising ID for app events. Validation failures contain
field paths, not input values. Production API errors retain structured event
indexes and at most 100 numeric codes per event, but discard Snap's free-form
error text because it may echo customer data. Incidental response request-ID
headers are retained only when they are valid bounded text and contain neither
the configured token nor asset ID. Production success uses a fixed adapter
message instead of Snap's free-form reason. Test-event and validation-log
workflows expose Snap's diagnostic strings by design; callers must scrub them
before logging.

## Event contracts

- A request contains between 1 and 2,000 events, Snap's documented batch limit,
  and is fully normalized before any network call. The adapter additionally
  applies a local 8 MiB encoded-request safety limit.
- Web and Mobile App events accept Unix seconds or milliseconds and cannot be
  more than seven days old. Offline events may carry older historical
  timestamps, but attribution remains bounded by Snap's 28-day swipe/click and
  seven-day view windows.
- Web and Mobile App events require an absolute HTTP(S) `event_source_url`.
- Mobile App events require `AppData`, an ATT value serialized as JSON `0` or
  `1`, and a fixed 16-slot `a2` or `i2` `extinfo` array.
- `PURCHASE` requires exact `custom_data.value` and an allowed currency.
- `LMU` and `DELETE` data-processing options are accepted only for Web events.
- Reuse `event_id` across CAPI, Pixel, and MMP sends so Snap can deduplicate
  equivalent events.

`ValidateEvents`, `GetValidationLogs`, and `GetValidationStats` implement the
official test-event endpoints. Validation logs cover test events received in
the preceding 24 hours. These tools do not confirm production attribution.

For production submission, HTTP 429, 5xx, and transient transport failures are
retryable only when every event has a non-empty stable `event_id`; otherwise
the error is deliberately marked permanent to prevent duplicate conversions.
Test submission and validation diagnostic reads are retry-safe. The adapter
does not retry or queue automatically, and Snap does not define an idempotency
request header.

## Deliberate exclusions

- Dynamic Travel Ads parameters;
- Genesis CSV/JSON batch-file upload;
- LaunchPAD forwarding and Privacy-Enhancing Technologies;
- Pixel, Snap App, and Offline Event Set administration; and
- automatic retry, queueing, or logging of raw events and access tokens.

No credentialed request has been run against a production asset. Package builds
and production-file static checks are the current verification baseline.
